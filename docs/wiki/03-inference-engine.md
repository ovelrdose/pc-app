# 3. Машина вывода

> Разделы 3.1–3.4 и 3.7 сверены с кодом: 2026-10-29. Раздел 3.5 (обратный вывод) и загрузка снимков из §3.6 пока описывают целевое поведение (этапы 4–5).

Машина вывода — часть ядра, которая применяет правила к фактам. Она не содержит ни одного знания о компьютерах. Всё, что она умеет:
- находить правила, условия которых выполнены;
- выбирать, какое применить;
- выполнять их действия;
- записывать каждый шаг в журнал.

Поэтому система меняет поведение, когда меняются правила, а код при этом остаётся прежним (подробнее в [§3.6](#36-как-ядро-подхватывает-новые-правила)).

---

## 3.0 Чем это отличается от «дерева вопросов»

Многие простые экспертные системы устроены как **дерево решений**: вопрос → в зависимости от ответа правило А, Б или В → следующий вопрос → … → одно финальное правило с ответом. Путь один, и в каждый момент работает одно правило.

```
 Дерево решений                         Наша система (продукционная)
 ──────────────                         ────────────────────────────
      [вопрос 1]                         все ответы клиента сразу
     /    |    \                                  │
    А     Б     В                                 ▼
   / \                                  ┌── рабочая память (факты) ──┐
  Г   Д   ← финальное правило           │                            │
                                        │  правила «смотрят» на неё; │
 Один путь, один итог.                  │  каждое, чьё условие       │
                                        │  выполнено, добавляет      │
                                        │  свой вывод                │
                                        └────────────────────────────┘
                                         Срабатывают десятки правил,
                                         итог складывается из всех.
```

У нас дерево не подходит: ответы клиента **комбинируются**. Основная задача игры, иногда монтаж, 1440p, 165 Гц, белый корпус, бюджет 120 000 ₽, уже есть видеокарта. Дереву понадобилась бы отдельная ветка на каждое сочетание, а их десятки тысяч. В продукционной системе каждое правило отвечает за **одну мысль** («монтаж → нужно больше памяти»). Для конкретного клиента срабатывают все подходящие правила сразу, и их выводы складываются.

**Аналогия.** Дерево решений — анкета «если да, переходите к вопросу 7». Продукционная система — консилиум специалистов: все слушают ответы клиента, и каждый говорит, когда речь заходит о его теме. Сказанное одним может навести на мысль другого: «раз главный сценарий игры» → «значит, нужна видеокарта посильнее» → «значит, на неё 40% бюджета».

**Финального правила нет.** Результат — это набор накопленных выводов (требования и доли бюджета), по которым потом подбираются детали.

**Похожий на дерево режим у нас тоже есть.** Это обратный вывод ([§3.5](#35-обратный-вывод-от-гипотезы-к-фактам)): «потянет ли сборка игру X?». Там система идёт от одной цели вниз по условиям и при нехватке данных задаёт клиенту вопрос.

## 3.1 Прямой вывод: от фактов к выводам

Используется на этапе профилирования: из ответов клиента выводятся требования и бюджет. Это движение **от данных к цели**.

### Цикл «распознавание — действие»

```
            ┌──────────────────────────────────────────────┐
            ▼                                              │
  ① СОПОСТАВЛЕНИЕ: какие правила стали применимы?          │
            │                                              │
  ② НАБОР КОНФЛИКТОВ: все применимые правила               │
            │                                              │
  ③ ВЫБОР: одно правило по стратегии (§3.2)                │
            │                                              │
  ④ ДЕЙСТВИЕ: записать новые факты, сделать запись в трассе│
            │                                              │
            └── появились новые факты? ── да ──────────────┘
                         │ нет
                         ▼
                     ОСТАНОВ
```

1. **Сопоставление.** Ядро проверяет не все 531 правило на каждом шаге, а только те, что зависят от изменившихся фактов. Для этого при загрузке правил строится **индекс «факт → правила»**: например, от факта «какая видеокарта нужна играм клиента» зависят четыре правила класса игровой нагрузки (PRF-052 … PRF-055) и требования REQ-053, REQ-056; от `user.resolution` — бюджетные BUD-009, BUD-010 и несколько правил проверки. Когда меняется факт, перепроверяются только зависящие от него правила.
2. **Набор конфликтов.** Применимых правил может оказаться несколько. Набор конфликтов — их полный список с конкретными значениями, на которых сработали условия.
3. **Выбор** одного правила по стратегии разрешения конфликтов (§3.2).
4. **Действие.** Правило записывает новые факты или меняет уверенность существующих. Шаг попадает в трассу.
5. Если новые факты «разбудили» другие правила, цикл продолжается. Если применимых правил не осталось, вывод закончен.

### Пример цепочки

Ответы: в основном игры, иногда монтаж (веса 1.0 и 0.3), монитор 2K на 144–180 Гц, игры не названы, бюджет 120 000 ₽. До вывода система уже посчитала, что эталонной игре (Cyberpunk 2077) для 60 кадров в 2K нужна видеокарта с индексом 122.

```
шаг 1  PRF-011  ЕСЛИ вес игр ≥ 0.4 и наибольший ТО главный сценарий = игры        (cf 1.00)
шаг 2  PRF-021  ЕСЛИ вес монтажа ≥ 0.25        ТО вторичный сценарий = монтаж    (cf 0.30)
шаг 3  PRF-054  ЕСЛИ игры И играм нужен индекс 120–185 ТО нагрузка «высокая»      (cf 0.90)
шаг 4  REQ-024  ЕСЛИ монтаж ≥ 0.25             ТО ОЗУ ≥ 32 ГБ                     (cf 0.24)
шаг 5  REQ-053  ЕСЛИ игры — основная задача    ТО видеокарта с индексом ≥ 122     (cf 0.90)
шаг 6  BUD-009  ЕСЛИ игры И 1440p              ТО доля GPU = 40%                  (cf 0.90)
шаг 7  BUD-021  ЕСЛИ ОЗУ ≥ 32                  ТО доля ОЗУ = 9%                   (cf 0.24)
…
итог: ~20 сработавших правил, ~25 новых фактов
```

Каждый шаг опирается на предыдущие: REQ-024 не мог сработать, пока PRF-021 не установил вторичный сценарий.

Порядок PRF → REQ → BUD в этом примере ядро не задаёт: группы для него не существуют. Правила PRF, REQ и BUD лежат в одном общем наборе, и порядок складывается из того, какое правило каким фактам ждёт. Подробнее в разделе [«Как группы перетекают друг в друга»](02-knowledge.md#как-группы-перетекают-друг-в-друга).

## 3.2 Какое правило применить первым

Если применимо несколько правил, порядок определяется так, по убыванию важности критерия:

1. **Приоритет** (`priority`). Правила совместимости и безопасности имеют высокий приоритет, мягкие предпочтения — низкий.
2. **Специфичность.** Более конкретное правило важнее общего. Правило «игры И 4K И трассировка лучей» (3 условия) сработает раньше правила «игры» (1 условие). Это отражает логику эксперта: частный случай уточняет общий.
3. **Свежесть.** Правило, опирающееся на только что выведенные факты, идёт раньше. Так рассуждение «развивает мысль», а не прыгает между темами.

**Рефракция.** Одно и то же правило на одних и тех же данных срабатывает только один раз. Без этого правило «ЕСЛИ игры ТО доля GPU = 40%» срабатывало бы бесконечно. «Те же данные» — это те же факты с теми же значениями **и той же уверенностью**. Если уверенность посылки выросла (второе правило подтвердило тот же факт), правило срабатывает ещё раз и **обновляет** свой вывод.

**Если правило не вычисляется.** Бывает, что формула в правиле не может быть посчитана: деление на ноль, сравнение числа со строкой. Такое правило пропускается, в трассу записывается ошибка с его кодом, а вывод продолжается.

**Защита от зацикливания.** Если два правила начинают бесконечно переписывать друг друга, ядро останавливается после 10 000 шагов и сообщает об ошибке в базе знаний. На практике до этого не доходит: циклы ищутся при проверке перед публикацией ([страница 7](07-updates.md)).

## 3.3 Конфликты значений

Два правила могут вывести для одного факта **разные значения**. Например, BUD-009 даёт «доля GPU = 40%», а BUD-014 — «доля GPU = 45%». Так бывает не только с числами: одно правило может решить «главный сценарий = игры», другое — «монтаж».

- Побеждает значение с **большей уверенностью**.
- При равной уверенности побеждает **более специфичное** правило.
- Ответ клиента важнее любого правила: правило не может «перекричать» то, что клиент сказал сам.
- После того как все доли бюджета выведены, они **нормируются**: если их сумма получилась 104%, каждая доля пропорционально уменьшается, чтобы вышло ровно 100%.

Обе версии остаются в трассе, и в экспертном режиме видно, какое правило «проиграло» и почему.

## 3.4 Уверенность (CF)

### Зачем

Ответы клиента часто размыты: «в основном играю, иногда монтирую», «не знаю, какой монитор». Знания эксперта тоже не абсолютны: «для монтажа нужно 32 ГБ» верно в большинстве случаев, но не всегда. Поэтому у каждого факта и правила есть **коэффициент уверенности** (CF) от 0 до 1. Это метод классической медицинской экспертной системы MYCIN.

### Откуда берётся уверенность фактов клиента

| Ответ | Уверенность |
|---|---|
| «Точно», конкретное значение | 1.0 |
| «Скорее да» | 0.6 |
| Задача: основная / дополнительная | вес 1.0 / 0.3 для факта «клиент этим занимается» |
| «Не знаю» | Факт не записывается; решение принимают правила, которым он не нужен, или значения по умолчанию |

### Как уверенность проходит через правило

```
уверенность условия:
    «все из» (И)   → минимальная из уверенностей
    «любое из» (ИЛИ) → максимальная
    «не»           → 1 − уверенность

уверенность вывода = уверенность правила × уверенность условия
```

**Пример.** REQ-024 «ЕСЛИ монтаж ТО ОЗУ ≥ 32 ГБ» имеет cf 0.8. Вес монтажа у клиента 0.3. Вывод: «ОЗУ ≥ 32 ГБ» с уверенностью 0.8 × 0.3 = **0.24**.

### Когда два правила приходят к одному выводу

Если факт подтверждают два независимых правила, уверенность растёт, но не превышает 1:

```
обе положительные:  a + b × (1 − a)
пример: 0.24 и 0.5  →  0.24 + 0.5 × 0.76 = 0.62
```

Два независимых свидетеля убедительнее одного. Есть формулы и для отрицательных уверенностей («скорее нет»), и для случая, когда одно правило «за», а другое «против».

**Повторное срабатывание не раздувает уверенность.** Каждое правило — один свидетель. Если оно сработало ещё раз (например, его посылка стала увереннее), его прежнее «показание» заменяется новым, а не добавляется к старому. Пример: REQ-001 вывел «нужно ≥ 1 ТБ» с уверенностью 0.5, потом его посылка укрепилась до 0.75, и он сработал снова. Итог — 0.75, а не 0.5 и 0.75 вместе (0.875).

### Порог

Факт считается **установленным**, если его уверенность ≥ **0.2**. Ниже порога он остаётся в памяти, но условия правил его не видят. Формула, которая ссылается на такой (или отсутствующий) факт, считается невыполненной.

**Как считается уверенность формулы.** Если условие — формула (`мощность БП < (TDP + TBP + 75) × 1.3`), её уверенность равна наименьшей уверенности фактов, которые в ней участвуют. Формула без фактов («всегда») имеет уверенность 1.

На этапе подбора уверенность влияет на силу требований. Требование с уверенностью ≥ 0.5 считается **обязательным**: эконом-вариант обязан его выполнить. Требование с меньшей уверенностью **желательно**: за его выполнение сборка получает баллы, но без него допустима.

### Где уверенности нет

Правила совместимости всегда «да/нет». Сокет либо подходит, либо нет, «на 70% совместимо» не бывает. Проверка при публикации не даст сохранить правило совместимости с уверенностью меньше 1.

## 3.5 Обратный вывод: от гипотезы к фактам

> Сверено с кодом: 2026-10-29. Если не хватает характеристики сборки, условие **опровергнуто** («в сборке этого нет»); если не хватает ответа клиента — **неизвестно**, и система задаёт вопрос (разрешение, комфортный FPS).

### Когда используется

- Клиент спрашивает: **«Потянет ли эта сборка Cyberpunk 2077 на ультра в 1440p?»**
- «Почему не эта деталь?» ([страница 6](06-explanations.md)).
- «Можно ли вообще выполнить мои требования в этот бюджет?» ([страница 4](04-configurator.md#47-если-требования-невыполнимы)).

### Как работает

Система берёт **цель** и ищет правила-цели (`goal`), которые могут её доказать. Условия такого правила становятся **подцелями**, и для каждой процесс повторяется. Получается дерево:

```
ЦЕЛЬ: «Cyberpunk 2077 пойдёт на ультра в 1440p»
│   правило GEN-GAME-CP2077-ULTRA: верно, ЕСЛИ все подцели верны
│
├── ПОДЦЕЛЬ: FPS ≥ 60 ?
│     │ встроенный расчёт модели производительности
│     ├── потолок видеокарты:  71 FPS
│     ├── потолок процессора:  95 FPS
│     └── итог: 71 FPS (±15%)                          ✅ доказано
│
├── ПОДЦЕЛЬ: видеопамять ≥ 12 ГБ ?
│     └── в сборке: 16 ГБ                              ✅ доказано
│
└── ПОДЦЕЛЬ: ОЗУ ≥ 16 ГБ ?
      └── в сборке: 32 ГБ                              ✅ доказано

ОТВЕТ: ДА, ≈ 71 FPS
```

Чем подцель может быть доказана:
- **фактом из памяти**: характеристикой детали, ответом клиента;
- **встроенным расчётом**: прогнозом FPS или бенчмарка ([страница 5](05-performance.md));
- **другим правилом-целью**: дерево может быть многоуровневым;
- **вопросом клиенту**. Если факта не хватает и его можно спросить, система **задаёт вопрос**. Пример: «Какой FPS для вас комфортен: 60, 90 или 144?». После ответа доказательство продолжается. Так работают диагностические экспертные системы.

У каждого узла три возможных исхода: **доказано**, **опровергнуто** (с причиной: «видеопамять 8 ГБ < 12 ГБ») или **неизвестно** (не хватает данных). Клиент видит дерево целиком.

### Переменные

Правила-цели используют переменные. Одно правило «игра пойдёт на пресете P в разрешении R, если FPS ≥ целевого» работает для любого разрешения: при проверке переменная `$resolution` подставляется из вопроса клиента или его профиля.

## 3.6 Как ядро подхватывает новые правила

Это ключевое свойство экспертной системы: **знания отделены от механизма**.

### Почему коду не нужно знать о правилах

В коде ядра нет ни одного «если сокет AM5…». Код умеет только:
- читать правило (условие, действие, приоритет, уверенность);
- проверять условие на фактах;
- выполнять действие одного из фиксированных типов: записать факт, отсеять товар, запретить сочетание, добавить баллы, предупредить, предложить замену;
- записывать трассу.

Поэтому, когда инженер знаний добавляет правило «ЕСЛИ стриминг И видеокарта AMD ТО предупредить о качестве кодировщика», ядро начинает его применять, хотя раньше о стриминге и кодировщиках ничего «не знало».

### Что происходит при публикации базы знаний

```
Инженер нажимает «Опубликовать»
        │
        ▼
① Проверка всей базы (противоречия, циклы, опечатки в слотах, эталонные кейсы)
        │ всё в порядке
        ▼
② Создаётся СНИМОК v15: замороженная копия всех включённых правил и справочников
        │
        ▼
③ Ядро загружает снимок и КОМПИЛИРУЕТ его:
     • каждое условие разбирается в готовое к быстрому вычислению дерево
     • каждая формула проверяется и разбирается
     • для каждого правила считается специфичность (число условий)
     • строится индекс «факт → правила»
     • правила раскладываются по видам: inference / filter / compat / score / validate / goal
        │
        ▼
④ Новые консультации идут по v15.
   Консультации, начатые до публикации, доходят до конца на v14:
   клиент не увидит, как правила поменялись посреди подбора.
```

Компиляция занимает доли секунды. Перезапуск сервера не нужен.

### Как новое правило «встраивается» в рассуждение

Ядру не нужно объяснять, куда поставить новое правило. Его место определяется данными:

| Свойство правила | Что оно определяет |
|---|---|
| `kind` | На каком этапе применяется: профилирование, фильтр, поиск, оценка, проверка, обратный вывод |
| Факты в условии | Когда просыпается (через индекс «факт → правила») |
| `priority` и специфичность | Порядок относительно соседей |
| `cf` | Сила вывода и его вес в сочетании с другими правилами |
| Факты в действии | Какие правила оно «разбудит» дальше |

**Пример.** Инженер добавляет правило `REQ-041`: «ЕСЛИ стриминг ≥ 0.3 ТО видеокарта с аппаратным кодировщиком AV1, cf 0.7».
- Ядро видит `kind: inference` и применяет правило на этапе профилирования.
- По индексу оно будет проверяться при каждом изменении `profile.streaming_weight`.
- Его вывод `req.gpu_av1_encoder` попадёт в фильтр кандидатов, если существует filter-правило, которое этот факт читает. Если такого правила нет, проверка при публикации предупредит: «факт `req.gpu_av1_encoder` выводится, но нигде не используется».

### Как ядро подхватывает новые товары

Похожим образом, но без публикации:
- у каталога есть **номер ревизии**, и любое изменение (новый товар, цена, наличие) увеличивает его;
- перед каждым подбором ядро сверяет номер. Если он изменился, каталог перечитывается в память;
- новый товар сразу проходит через все существующие правила. Новая видеокарта автоматически проверяется на совместимость с корпусами, блоками питания и т.д., писать для неё отдельные правила не нужно.

### Чего ядро без программиста не умеет

| Изменение | Нужен программист? |
|---|---|
| Новое правило, правка правила, отключение правила | Нет |
| Новая игра, программа, сокет, чипсет в справочнике | Нет |
| Новый товар, новая цена | Нет |
| Новая характеристика детали (слот), например «поддержка PCIe 6.0» | **Да**: новый слот во фрейме + миграция БД. После этого правила могут его использовать |
| Новая категория, например «Мониторы» | **Да**: новый фрейм, место в порядке подбора, интерфейс |
| Новый тип действия правила, кроме шести существующих | **Да** |
| Новая функция в формулах правил | **Да**: функцию нужно добавить в белый список интерпретатора |

## 3.7 Детерминизм

Одинаковые ответы на одном и том же снимке базы знаний и одной ревизии каталога **всегда дают одинаковый результат и одинаковую трассу**. Это важно:
- для тестов (эталонные кейсы);
- для воспроизведения: каждая сборка помнит снимок и ревизию каталога, на которых посчитана;
- для доверия: клиент, нажавший «Подобрать» дважды, не получит две разные «лучшие» сборки.
