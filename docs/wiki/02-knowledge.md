# 2. Знания: фреймы, правила, факты

В системе используется **гибридная модель знаний**:
- **фреймы** описывают, *что существует*: какие бывают детали и какие у них свойства;
- **продукционные правила** описывают, *как рассуждать*: что из чего следует;
- **факты** описывают *текущую ситуацию*: что известно о конкретном клиенте и его сборке.

---

## 2.1 Фреймы

> Раздел 2.1 (фреймы деталей) сверен с кодом: 2026-10-29. Фреймы «Профиль клиента», «Сценарий», «Игра / Программа» и «Сборка» пока описывают целевое поведение.

### Что это

Фрейм — шаблон описания объекта. У шаблона есть **слоты**, то есть поля характеристик. Конкретный товар — заполненный экземпляр фрейма.

```
Фрейм «Процессор»                    Экземпляр: Ryzen 5 7600
├─ бренд            (из «Комплектующее»)   ├─ бренд:           AMD
├─ цена, ₽          (из «Комплектующее»)   ├─ цена:            18 990 ₽
├─ сокет            AM4 | AM5 | LGA1700…   ├─ сокет:           AM5
├─ ядер / потоков   1…128                  ├─ ядер / потоков:  6 / 12
├─ TDP, Вт          10…400                 ├─ TDP:             65 Вт
├─ встроенная графика  да/нет              ├─ встр. графика:   да
├─ индекс одноядерный  > 0                 ├─ индекс single:   100
└─ индекс многоядерный > 0                 └─ индекс multi:    100
```

### Иерархия и наследование

```
Комплектующее (бренд, модель, цена, наличие, цвет, RGB, год выпуска)
 ├── Процессор        (сокет, ядра, TDP, iGPU, индексы…)
 ├── Материнская плата (сокет, чипсет, форм-фактор, тип памяти, слоты M.2…)
 ├── Оперативная память (тип, объём, частота, тайминги, высота…)
 ├── Видеокарта       (видеопамять, длина, TBP, разъёмы питания, индексы…)
 ├── Накопитель
 │    ├── SSD         (интерфейс, скорость, объём)
 │    └── HDD         (объём, обороты)
 ├── Блок питания     (мощность, сертификат, модульность, разъёмы)
 ├── Корпус           (форм-факторы плат, макс. длина GPU, макс. высота кулера…)
 ├── Кулер процессора (тип, сокеты, высота, рассеиваемая мощность)
 └── Корпусной вентилятор (размер, шум, RGB)
```

Слоты «Комплектующего» (цена, бренд, цвет…) есть у каждого потомка автоматически. Правило «если клиент хочет белую сборку, то цвет должен быть белым» поэтому работает для любой категории сразу.

### Что ещё умеют фреймы

- **Ограничения слотов.** У каждого слота есть тип, единицы, допустимый диапазон или список значений. Если в каталог пытаются загрузить видеокарту длиной «abc» или 2000 мм, система отклоняет строку и объясняет причину:
  ```
  строка 7: «Длина» (length_mm) = «abc»: ожидается целое число
  строка 9: «Длина» (length_mm) = «2000»: должно быть не больше 400
  ```
- **Проверки между слотами.** Некоторые слоты проверяются вместе: потоков не меньше, чем ядер; частота в бусте не ниже базовой; объём комплекта памяти делится поровну между планками; NVMe-накопитель бывает только в формате M.2; размер радиатора указывают только у водяного охлаждения.
- **Открытые значения платформ.** Сокет, чипсет, форм-фактор и тип памяти — это не жёсткий список в программе, а просто строка. Фрейм примет «AM6», а то, что такой сокет пока неизвестен, заметит база знаний: товар получит статус «требует знаний» ([страница 7](07-updates.md#74-статусы-товаров)). Так новая платформа добавляется без программиста.
- **Значения по умолчанию.** Например, вентиляторов в упаковке — 1, товар «в наличии», цвет — чёрный, название собирается из бренда и модели («AMD» + «Ryzen 5 7600»).
- **Вычисляемые слоты.** У фрейма «Сборка» есть слоты, которые никто не вводит: «общая цена», «ожидаемое энергопотребление», «соотношение CPU/GPU». Они вычисляются при первом обращении.
- **Формы из фреймов.** Форма добавления товара в админке и колонки CSV-шаблона строятся по фрейму. Новый слот во фрейме сразу даёт новое поле в форме.

### Фреймы, которые не являются деталями

| Фрейм | Что описывает |
|---|---|
| Профиль клиента | Ответы визарда и всё, что из них выведено |
| Сценарий | Типовая задача (игры, монтаж…) и её особенности |
| Игра / Программа | Нагрузка, базовый FPS, требования к видеопамяти и памяти |
| Сборка | Набор деталей по категориям + вычисляемые характеристики |

## 2.2 Продукционные правила

### Что это

Правило — это «ЕСЛИ условие ТО действие» с человеческим объяснением:

```yaml
code: BUD-014
name: 4K-гейминг смещает бюджет в видеокарту
kind: inference
priority: 500
cf: 0.9
when:                                 # ЕСЛИ
  all:
    - user.resolution = 2160p
    - profile.gaming_weight ≥ 0.5
then:                                 # ТО
  - budget.share.gpu := 0.45
  - budget.share.cpu := 0.18
explain: "Для игр в 4K главная нагрузка ложится на видеокарту, поэтому ей отдаётся ~45% бюджета."
```

### Из чего состоит правило

| Часть | Смысл |
|---|---|
| `code` | Уникальный код (`BUD-014`). Никогда не переиспользуется, даже после удаления правила |
| `name` | Короткое название для людей |
| `kind` | Вид правила: определяет, на каком этапе и как оно применяется (ниже) |
| `priority` | Важность. Когда применимо несколько правил, раньше срабатывает более важное |
| `cf` | Уверенность эксперта в правиле, от 0 до 1 ([страница 3](03-inference-engine.md#34-уверенность-cf)) |
| `when` | Условие. Можно комбинировать: «все из» (`all`), «любое из» (`any`), «не» (`not`) |
| `then` | Что сделать, если условие выполнено |
| `explain` | Текст объяснения для клиента. В него подставляются значения: «БП {мощность} Вт слабоват» |

### Какие бывают условия

> Условия, действия и проверки отдельного правила сверены с кодом: 2026-10-29.

- **Сравнение факта со значением:** `видеопамять ≥ 12`, `сокет = AM5`, `цвет в [белый, серебристый]`.
- **Сравнение двух фактов:** `сокет процессора = сокет платы`.
- **Формула:** `мощность БП < (TDP процессора + TBP видеокарты + 75) × 1.3`. Формулы вычисляет собственный безопасный интерпретатор: в правиле можно использовать только арифметику (без возведения в степень), сравнения, «и / или / не», «входит в список» и несколько разрешённых функций: `min`, `max`, `ceil`, `floor`, `abs`, `round`, `len`, `contains`. Никакой «настоящий» код из правила выполнить нельзя: попытка обратиться к чему-то кроме фактов и этих функций отклоняется ещё при загрузке правила.

### Шесть видов правил

| Вид | Когда применяется | Что делает | Пример |
|---|---|---|---|
| **inference** (вывод) | Этап профилирования | Из известных фактов выводит новые | ЕСЛИ монтаж ≥ 30% ТО ОЗУ ≥ 32 ГБ |
| **filter** (фильтр) | Этап фильтрации | Убирает отдельные товары из рассмотрения | ЕСЛИ «белая сборка» ТО корпус должен быть белым |
| **compat** (совместимость) | Этап поиска | Запрещает несовместимые сочетания | ЕСЛИ сокет CPU ≠ сокет платы ТО нельзя |
| **score** (оценка) | Этап оценки | Добавляет баллы за желательное | ЕСЛИ «задел на будущее» и платформа AM5 ТО +баллы |
| **validate** (проверка) | Этап проверки | Проверяет готовую сборку: ошибка, предупреждение или совет | ЕСЛИ CPU раскрывает GPU < 70% ТО предупредить |
| **goal** (цель) | Обратный вывод | Описывает, при каких условиях верна гипотеза | «Игра X пойдёт на ультра, ЕСЛИ FPS ≥ 60 И VRAM ≥ 12 ГБ» |

### Зачем нужен вид, если правила и так ждут своих фактов

#### Один блокнот и «то, что в руках»

Блокнот у консультации **один**: всё, что известно о клиенте (ответы, профиль, требования, бюджет). Его читают все правила.

Но многие правила говорят не только о клиенте, а ещё и о **конкретной вещи**: этом корпусе, этой паре «процессор + плата», этой сборке. Такой вещи в блокноте нет. Программа сама берёт её «в руки», то есть подставляет, и проверяет правилом. Затем берёт следующую.

Так работает продавец-консультант в магазине:

```
 1. Поговорил с клиентом, записал в блокнот          ← inference
    «геймер, 1440p, хочет белую сборку, 120 000 ₽»

 2. Идёт вдоль полок, берёт в руки каждую коробку,   ← filter
    сверяет с блокнотом: «корпус чёрный — не берём»

 3. Раскладывает детали на столе: подходят ли        ← compat
    друг к другу? «сокеты разные — не соберётся»

 4. Сравнивает собранные варианты: какой лучше       ← score
    для этого клиента?

 5. Финально осматривает три лучших варианта         ← validate

 6. Клиент спрашивает: «А Cyberpunk пойдёт?»         ← goal
    Консультант проверяет одну конкретную сборку
```

Блокнот всё время один и тот же. Меняется только то, **что в руках**. Вид правила и говорит, что должно быть в руках, чтобы правило имело смысл:

| Вид | Что в руках | Пример: читает блокнот + то, что в руках |
|---|---|---|
| inference | ничего, только блокнот | ЕСЛИ игры И 1440p ТО видеокарта ≥ «средний+» |
| filter | один товар | ЕСЛИ клиент хочет белую сборку И **этот корпус** не белый ТО убрать |
| compat | несколько деталей вместе | ЕСЛИ сокет **этого процессора** ≠ сокет **этой платы** ТО нельзя |
| score | готовая сборка | ЕСЛИ клиенту важен задел И **в сборке** платформа AM5 ТО +баллы |
| validate | один из трёх итоговых вариантов | ЕСЛИ **в сборке** одна планка памяти ТО совет: лучше две |
| goal | сборка + вопрос клиента | Игра X пойдёт, ЕСЛИ FPS **этой сборки** ≥ 60 |

Правило фильтра без товара в руках бессмысленно: «корпус не белый» — какой корпус? Поэтому его нельзя просто «разбудить фактом» в блокноте. Его нужно применить к каждому товару по очереди, и вид сообщает программе, что делать именно так.

#### Почему этапы идут по очереди

Консультант не ходит к полкам, пока не дослушал клиента. Пока идёт разговор, выводы ещё меняются: сначала «хватит 8 ГБ видеопамяти», потом выясняется, что нужно 12. Если начать отбирать товары раньше, отберёшь лишнее.

Поэтому правила с товаром в руках ждут не просто появления факта в блокноте, а **конца разговора**, когда все требования окончательные.

#### Где «ждать свой факт» работает

- **В разговоре (inference):** правила срабатывают цепочкой, каждое — когда в блокноте появилось то, что ему нужно.
- **На столе (compat):** правило «сокет процессора = сокет платы» срабатывает, как только на столе оказались процессор и плата. Блок питания оно не ждёт. Неподходящее сочетание отбрасывается сразу, и его не достраивают.

#### Что правилу разрешено делать

| Вид | Действие |
|---|---|
| inference | записать в блокнот новый вывод о клиенте |
| filter | убрать товар (с причиной) |
| compat | запретить сочетание |
| score | добавить или снять баллы |
| validate | ошибка, предупреждение или совет |
| goal | доказать или опровергнуть гипотезу |

Правило не может сделать чужую работу: например, фильтр не может дописать в блокнот вывод о клиенте. Такое правило не загрузится: ошибка видна сразу, ещё до проверки всей базы. Ещё одно ограничение: правила вывода пишут только в «профиль», «требования» и «бюджет», но не в ответы клиента.

### Группы правил

Вид (`kind`) говорит, **как** правило применяется. Группа говорит, **о чём** оно. Группа видна по префиксу кода: `BUD-014` — правило из группы BUD, номер 14. Префиксы — сокращения английских слов.

#### Группа — это тема, а не набор условий и не шаг программы

Группа объединяет правила, которые отвечают на **один вопрос** («кто клиент?», «сколько тратить?»). Условия у правил одной группы разные: у PRF-003 «вес игр ≥ 0.5», у PRF-025 «выбран цвет или RGB». Общее у них только то, **что** они выясняют, то есть какие факты записывают (PRF пишет `profile.*`, REQ — `req.*`, BUD — `budget.*`).

**Ядро групп не видит.** Префикс нужен людям: правила лежат в файлах по группам (`PRF.yaml`, `REQ.yaml`…), их удобно искать, считать и фильтровать в редакторе. Если переименовать `REQ-024` в `BUD-099` и ничего больше не менять, система будет работать так же.

На порядок работы влияют три вещи, и ни одна из них не группа:

| Что | На что влияет |
|---|---|
| **Вид** (`kind`) | На каком **этапе** подбора правило применяется. Этапы действительно идут строго по очереди |
| **Факты в условии** | **Когда** правило может сработать внутри этапа: не раньше, чем эти факты появятся |
| **Приоритет, специфичность, свежесть** | Какое из нескольких одновременно готовых правил сработает **первым** ([§3.2](03-inference-engine.md#32-какое-правило-применить-первым)) |

#### Как группы перетекают друг в друга

Переходы бывают двух типов.

**1. Внутри профилирования: по цепочке фактов, без очереди.** PRF, REQ и BUD (все `inference`) загружаются в ядро **одним общим набором** и работают в одном цикле прямого вывода. Ядро не говорит «сначала все PRF, потом все REQ». На каждом шаге оно берёт любое правило, условия которого уже выполнены.

Порядок «PRF → REQ → BUD» получается сам, потому что правила читают выводы друг друга:

```
 ответы клиента (user.*)
       │
       ▼
 PRF-003  ЕСЛИ вес игр ≥ 0.5 ТО главный сценарий = игры ──► profile.main = игры
                                                                  │
       ┌──────────────────────────────────────────────────────────┘
       ▼   (REQ-011 «спал», пока не было profile.main; теперь проснулся)
 REQ-011  ЕСЛИ игры И 1440p ТО класс видеокарты ≥ «средний+» ──► req.gpu_class
                                                                  │
       ┌──────────────────────────────────────────────────────────┘
       ▼
 BUD-009  ЕСЛИ класс GPU ≥ «средний+» И 1440p ТО доля GPU = 40% ──► budget.share.gpu
```

Поэтому порядок нестрогий:
- правило BUD, которому нужен только бюджет из ответов («ЕСЛИ бюджет < 50 000 ТО на корпус не больше 5%»), может сработать **на первом шаге**, раньше любого PRF;
- правило PRF, которое читает требование («ЕСЛИ нужна видеокарта ≥ "высокий" ТО подбирать её первой»), сработает **после** REQ.

Так и задумано: правило срабатывает, как только для него есть данные. Этап заканчивается, когда новых выводов больше не появляется.

**2. Между этапами: строгая очередь, передача через факты.** Этапы подбора идут друг за другом ([страница 4](04-configurator.md#41-пять-этапов)). Каждый этап применяет правила своего вида и передаёт следующему готовый результат:

```
 ① профилирование     PRF, REQ, BUD (inference)
        │  передаёт: требования req.*, доли бюджета budget.*, порядок категорий
        ▼
 ② фильтрация         FLT, часть GEN-CHP (filter) + требования из ①
        │  передаёт: списки допустимых товаров по категориям
        ▼
 ③ поиск              CMP, GEN-SKT, GEN-CHP, GEN-FF (compat)
        │  передаёт: сотни совместимых сборок
        ▼
 ④ оценка             SCR, BAL (score) + прогноз FPS
        │  передаёт: сборки с «полезностью»
        ▼
 ⑤ проверка           VAL, BAL (validate)
        │  передаёт: три варианта с предупреждениями
        ▼
 ⑥ по запросу         GOL, GEN-GAME, GEN-APP (goal) — обратный вывод
                      «Потянет ли эта сборка игру X?»
```

Обратной связи между этапами нет: фильтр не может «переспросить» профилирование. Если пользователь правит сборку (например, «сдвинуть бюджет к видеокарте»), конвейер запускается заново с изменёнными фактами.

**Почему BAL на двух этапах.** Группа — это тема, а этап задаёт вид. В теме «баланс» есть правила вида `score` («−баллы, если CPU слабее GPU») и вида `validate` («предупредить, если CPU раскрывает видеокарту меньше чем на 70%»). Они живут в одной группе, но работают на разных этапах.

#### Итог одной картинкой

```
 «Кто этот клиент?»        PRF  ─┐
 «Что ему нужно от железа?» REQ   ├─ профилирование (прямой вывод)
 «Сколько тратить на что?»  BUD  ─┘
            │
 «Что из каталога подходит?»       FLT  ── фильтрация
            │
 «Что с чем можно собрать?»        CMP + GEN-SKT/CHP/FF ── поиск
            │
 «Какая сборка лучше?»             SCR + BAL ── оценка
            │
 «Всё ли в порядке с итогом?»      VAL + BAL ── проверка
            │
 «Потянет ли игру X?»              GOL + GEN-GAME/APP ── обратный вывод (по запросу)
```

Это схема того, **о чём** думает система и в каком порядке обычно появляются выводы. Порядок между этапами (горизонтальные черты) строгий. Порядок PRF → REQ → BUD внутри профилирования — это порядок зависимостей между фактами, а не очередь вызова.

#### PRF — профилирование: «Кто этот клиент?»

**Задача:** превратить сырые ответы визарда в понимание клиента: главный и второй сценарии, игровая нагрузка, класс бюджета, что для клиента важно, даже если он не сказал этого прямо.

**Читает:** `user.*` (ответы). **Пишет:** `profile.*`.

| Пример | Условие → вывод |
|---|---|
| PRF-003 | ЕСЛИ вес «современных игр» ≥ 10% ТО учитывать сценарий с этим весом |
| PRF-011 | ЕСЛИ вес игр ≥ 40% И он самый большой ТО главный сценарий = игры |
| PRF-021 | ЕСЛИ вес монтажа ≥ 25%, но не самый большой ТО второй сценарий = монтаж |
| PRF-054 | ЕСЛИ игры И вашим играм нужна видеокарта с индексом 120–185 ТО игровая нагрузка «высокая» |
| PRF-045 | ЕСЛИ нужны RGB, стекло или белый цвет ТО внешний вид важен |
| PRF-049 | ЕСЛИ главное — офис, разработка или фото И игр нет ТО дискретная видеокарта не нужна |

Без PRF остальные правила пришлось бы писать прямо на ответах клиента, и каждое повторяло бы одну и ту же логику «кто он».

#### REQ — требования: «Что ему нужно от железа?»

**Задача:** перевести «кто клиент» в конкретные технические требования к деталям: минимумы, классы, нужна ли деталь вообще.

**Читает:** `profile.*`, `user.*`. **Пишет:** `req.*`.

| Пример | Условие → вывод |
|---|---|
| REQ-001 | ЕСЛИ дискретная видеокарта не нужна ТО без видеокарты, процессор со встроенной графикой |
| REQ-008 | ЕСЛИ современные игры И нагрузка «высокая» ТО от 8 ГБ видеопамяти |
| REQ-053 | ЕСЛИ игры — основная задача ТО видеокарта не слабее той, что нужна вашей самой требовательной игре для комфортного FPS |
| REQ-055 | ЕСЛИ вашей игре для комфортного FPS нужен процессор быстрее среднего ТО одноядерный индекс CPU не ниже нужного |
| REQ-025 | ЕСЛИ задачи требуют много памяти ТО ОЗУ ≥ 32 ГБ |
| REQ-033 | ЕСЛИ современные игры — основная задача и объём SSD не указан ТО SSD ≥ 1 ТБ |
| REQ-052 | ЕСЛИ клиент выбрал тип памяти (DDR4 или DDR5) ТО подбирать плату, процессор и память под него |

Уверенность требования решает, **обязательное** оно (≥ 0.5) или **желательное** ([страница 3](03-inference-engine.md#34-уверенность-cf)).

**Требования к видеокарте и процессору считаются по играм клиента.** Для каждой игры в справочнике записан комфортный FPS: соревновательные шутеры — 240, онлайн-игры — 100, одиночные — 60, стратегии — 45. Система берёт меньшее из комфортного FPS и частоты монитора и по модели производительности считает, какая видеокарта и какой процессор дадут столько кадров ([страница 5, §5.7](05-performance.md#57-зачем-спрашивать-монитор-и-как-считаются-требования-по-играм)). Результат попадает в рабочую память как **вычисляемые факты** «что нужно играм» (индексы, самая требовательная игра и её цель), а правила REQ и PRF на них ссылаются. Поэтому новая игра в справочнике подхватывается без правки правил. Класс игровой нагрузки (лёгкая / средняя / высокая / экстремальная) тоже выводится из этого требования, а не из монитора.

**8 ГБ видеопамяти и 16 ГБ ОЗУ — допустимый игровой минимум.** Обязательные требования не отсеивают видеокарты с 8 ГБ (кроме экстремальной нагрузки — обычно это 4K, — где нужна видеокарта топ-класса) и комплекты на 16 ГБ. Вместо запрета правила VAL-022 и VAL-023 предупреждают о рисках, а советы VAL-010 и BAL-028 подсказывают, куда расти (12+ ГБ видеопамяти, 32 ГБ ОЗУ). Так эконом-вариант остаётся доступным, а клиент видит, чем он рискует. Прежнее правило REQ-012 («12 ГБ видеопамяти для игр в 2K») выведено из базы; его код больше не используется.

**Объём SSD.** Если клиент ответил, сколько места нужно, система берёт его ответ. Если ответил «не знаю», объём зависит от основной задачи:
- современные игры — от 1 ТБ (одна игра занимает 70–150 ГБ);
- монтаж — от 2 ТБ;
- остальное — от 500 ГБ.

Когда современные игры — только дополнительная задача («в основном программирую, иногда играю»), система не требует 1 ТБ, но в сборке с меньшим SSD даёт совет BAL-031: «лучше SSD от 1 ТБ». Тот же совет появляется, если клиент сам выбрал 500 ГБ. Это общий принцип: жёсткие требования идут от основной задачи, а дополнительная задача даёт советы.

**Как задавать уверенность требований.** Если два правила требуют разного (16 и 32 ГБ), побеждает более уверенное ([§3.3](03-inference-engine.md#33-конфликты-значений)). А уверенность затухает по цепочке: «монтаж» (0.85) → «32 ГБ» (0.85) даёт 0.72. Поэтому базовые требования («игры → 16 ГБ») получают уверенность около 0.6: они ещё обязательные, но проигрывают более конкретным. Эту ошибку нашли эталонные кейсы при наполнении базы.

#### BUD — бюджет: «Сколько тратить на что?»

**Задача:** разделить бюджет клиента между категориями, чтобы деньги ушли туда, где они дают больше пользы именно в его задачах.

**Читает:** `profile.*`, `req.*`, `user.*`. **Пишет:** `budget.share.*` (доли от 0 до 1) и `budget.first_category`.

| Пример | Условие → вывод |
|---|---|
| BUD-001 | ЕСЛИ главное — современные игры ТО видеокарте 42%, процессору 17%, плате 10%… |
| BUD-002 | ЕСЛИ главное — киберспорт ТО видеокарте 36%, процессору 22% (важнее частота кадров, чем картинка) |
| BUD-009 | ЕСЛИ игры в 4K ТО видеокарте 48% |
| BUD-020 | ЕСЛИ видеокарта не нужна ТО процессору 30% |
| BUD-021 | ЕСЛИ «задел на будущее» ТО плате 12% |
| BUD-023 | ЕСЛИ игровая нагрузка высокая ТО видеокарту подбирать первой |

Доли нормируются к 100% по тем категориям, которые реально подбираются. Именно эту задачу из ТЗ называют «оптимизацией бюджета».

#### FLT — фильтры: «Что из каталога вообще подходит?»

**Задача:** до сборки убрать товары, которые клиенту точно не подходят, по одному.

**Проверяет:** `cand.*` (товар-кандидат) против `req.*` и `user.*`. **Действие:** отсеять товар с причиной.

| Пример | Условие → действие |
|---|---|
| FLT-001 | ЕСЛИ товара нет в наличии ТО отсеять |
| FLT-002 | ЕСЛИ видеопамять кандидата меньше требуемой ТО отсеять видеокарту |
| FLT-008 | ЕСЛИ нужна встроенная графика И у процессора её нет ТО отсеять процессор |
| FLT-016 | ЕСЛИ цвет корпуса не тот, что выбрал клиент ТО отсеять корпус |
| FLT-019 | ЕСЛИ клиент предпочитает AMD И процессор другого бренда ТО отсеять |
| FLT-027 | ЕСЛИ клиент выбрал тип памяти И у платы или комплекта памяти другой ТО отсеять |
| FLT-025 | ЕСЛИ рабочей станции нужна плата с хорошим питанием И у кандидата простое ТО отсеять |

Исключения, которые клиент делает правкой («не предлагать MSI»), и товары со статусом «неполный» отсеиваются самой программой, без правил. Причина отсева сохраняется: из неё строится ответ на «почему не эта деталь?».

#### CMP — совместимость: «Что с чем можно собрать?»

**Задача:** не допустить физически или электрически несовместимых сочетаний. Это задача «обеспечение совместимости» из ТЗ.

**Проверяет:** пары и группы деталей сборки (`build.*`). **Действие:** запретить сочетание. Уверенность всегда 1.0: совместимость либо есть, либо нет.

| Пример | Условие → действие |
|---|---|
| CMP-001 | ЕСЛИ сокет процессора ≠ сокету платы ТО нельзя |
| CMP-004 | ЕСЛИ длина видеокарты > макс. длины для корпуса ТО нельзя |
| CMP-007 | ЕСЛИ мощность БП меньше потребления сборки × 1.2 ТО нельзя |
| CMP-009 | ЕСЛИ кулер рассеивает меньше TDP процессора ТО нельзя |
| CMP-016 | ЕСЛИ видеокарте нужен 12V-2x6, а у БП нет ни его, ни трёх 8-pin ТО нельзя |
| CMP-019 | ЕСЛИ видеокарты нет И у процессора нет встроенной графики ТО нельзя |

Ручные CMP — общие физические проверки по свойствам деталей. Однотипные таблицы совместимости (какой сокет с каким чипсетом, какая плата в какой корпус) вынесены в генерируемые GEN-SKT, GEN-CHP и GEN-FF.

#### BAL — баланс: «Не тормозит ли одна деталь другую?»

**Задача:** не допустить дисбаланса, когда мощная деталь не раскрывается из-за слабой. Это задача «балансировка системы» из ТЗ.

**Читает:** `build.*`, `profile.*` и прогноз `perf.*` (средний FPS в играх клиента, соотношение CPU/GPU, на сколько процессор раскрывает видеокарту). **Действия:** штраф или бонус к полезности на этапе оценки, предупреждение или совет на этапе проверки.

| Пример | Условие → действие |
|---|---|
| BAL-001 | ЕСЛИ современные игры И процессор раскрывает видеокарту меньше чем на 85% ТО штраф |
| BAL-003 | ЕСЛИ игры не в 4K И процессор мощнее нужного больше чем вдвое (соотношение > 2) ТО штраф «переплата за процессор» |
| BAL-005 | ЕСЛИ рабочая станция И многоядерный индекс < 120 ТО штраф |
| BAL-016 | ЕСЛИ сборка дороже 200 000 ₽ И плата с простым питанием ТО штраф |
| BAL-017 | ЕСЛИ игры И соотношение CPU/GPU от 0,85 до 2,0 ТО бонус «сбалансировано» |
| BAL-020 | ЕСЛИ процессор раскрывает видеокарту меньше чем на 80% ТО предупреждение «раскроет примерно на X%» |
| BAL-025 | ЕСЛИ имеющаяся у клиента видеокарта ограничивает новый процессор вдвое ТО совет заменить её |

Баланс считается по прогнозу FPS в играх клиента ([страница 5](05-performance.md#54-узкое-место-bottleneck)). Сначала правила сравнивали индексы процессора и видеокарты напрямую. Это давало ложные предупреждения: для RX 9070 XT с i5-14400F прогноз показывает упор в видеокарту, а сравнение индексов — в процессор. Штрафы учитываются уже при поиске, как только в сборке есть и процессор, и видеокарта ([страница 4](04-configurator.md#44-этап-3-поиск)).

#### SCR — оценка: «Какая из допустимых сборок лучше для клиента?»

**Задача:** учесть **мягкие** пожелания, без которых сборка допустима, но с ними лучше. Каждое правило добавляет баллы к полезности.

**Читает:** `build.*`, `profile.*`, `user.*`, `req.*`. **Действие:** `+баллы × уверенность`.

| Пример | Условие → баллы |
|---|---|
| SCR-004 | ЕСЛИ нужна подсветка И у вентиляторов есть RGB ТО +2 |
| SCR-009 | ЕСЛИ «задел на будущее» И память DDR5 ТО +3 |
| SCR-010 | ЕСЛИ «задел на будущее» И БП с запасом 60% ТО +3 |
| SCR-014 | ЕСЛИ желателен качественный БП И у него Gold и выше ТО +2 |
| SCR-019 | ЕСЛИ современные игры на высоких настройках И 16 ГБ видеопамяти ТО +4 |

FLT отсеивает **жёстко** (требования с уверенностью ≥ 0.5). SCR лишь **поощряет** («RGB — хорошо, но не обязательно»).

#### VAL — проверка: «Всё ли в порядке с итоговой сборкой?»

**Задача:** финальный «осмотр» готовой сборки целиком: то, что видно только на полной сборке, и практические советы.

**Читает:** всю сборку `build.*`, профиль и требования. **Действия:** ошибка (сборка отбрасывается), предупреждение или совет.

| Пример | Условие → действие |
|---|---|
| VAL-001 | ЕСЛИ память одной планкой ТО предупреждение «нет двухканального режима» |
| VAL-003 | ЕСЛИ остаётся больше 20% бюджета ТО совет «можно взять деталь мощнее» |
| VAL-006 | ЕСЛИ процессор с TDP ≥ 150 Вт на воздушном кулере ТО предупреждение |
| VAL-012 | ЕСЛИ видеокарта PCIe 5.0 в слоте 4.0 ТО предупреждение о потере 1–3% |
| VAL-018 | ЕСЛИ 4K на 165+ Гц И видеокарта не топовая ТО предупреждение «монитор не раскроется» |
| VAL-022 | ЕСЛИ игровая сборка И видеопамяти 8 ГБ ТО предупреждение о рисках: в новых играх на высоких и ультра (особенно в 2K) возможны подтормаживания, текстуры придётся снижать |
| VAL-023 | ЕСЛИ игровая сборка И ОЗУ 16 ГБ ТО предупреждение о рисках: мало запаса для фоновых программ и будущих игр |

Бюджет здесь не проверяется: сборки дороже бюджета отсекает сам поиск.

#### GOL — общие цели: «Правда ли, что…?»

**Задача:** правила для обратного вывода, не привязанные к конкретной игре. Они описывают, как доказывать общие гипотезы.

| Пример | Цель ← условия |
|---|---|
| GOL-002 | «Сборка готова к стримингу» ← ядер CPU ≥ 8 И видеокарта не слабее RTX 4060 И OBS работает на базовом уровне |
| GOL-003 | «Сборку удобно обновлять» ← запас БП 50% И свободные слоты памяти И ≥ 2 слотов M.2 |
| GOL-008 | «Киберспорт на 240 Гц» ← FPS в CS2 на средних настройках ≥ 240 (учитывает и видеокарту, и процессор) |

#### GEN-* — сгенерированные правила

Это однотипные правила, отличающиеся только данными. Писать их руками долго и чревато опечатками, поэтому их создаёт **генератор** из справочных таблиц.

| Группа | Из какой таблицы | Пример строки справочника → правила |
|---|---|---|
| **GEN-SKT** (сокеты) | Сокеты | «AM5: память DDR5, платформа перспективная» → `GEN-SKT-AM5-CHIPSET`: процессор AM5 только на платах с чипсетами AM5; `GEN-SKT-AM5-MEM`: только DDR5; `GEN-SKT-AM5-FUTURE`: +баллы за задел на будущее |
| **GEN-CHP** (чипсеты) | Чипсеты | «A620: без разгона, процессоры до 120 Вт» → `GEN-CHP-A620-TDP`: процессор мощнее 120 Вт нельзя; `GEN-CHP-A620-OC`: предупредить, что разблокированный множитель не пригодится |
| **GEN-FF** (форм-факторы) | Форм-факторы | «Mini-ITX — самая маленькая плата» → `GEN-FF-MINI-ITX-CASE`: только в корпус с поддержкой Mini-ITX; `GEN-FF-SIZE-MINI`: в компактный корпус только платы до Micro-ATX |
| **GEN-GAME** (игры) | Игры | Cyberpunk 2077 → 3 правила-цели: «пойдёт на средних / высоких / ультра», каждое: FPS не ниже целевого, хватает видеопамяти, ОЗУ от 16 ГБ |
| **GEN-APP** (программы) | Программы | Blender → 2 правила-цели: «базовый уровень» (16 ГБ, 6 ядер, 8 ГБ видеопамяти) и «профессиональный» (64 ГБ, 12 ядер, 16 ГБ) |

Сгенерированные правила **не правят руками**: правят справочник и запускают генерацию заново ([страница 7](07-updates.md#73-справочники-и-сгенерированные-правила)). Проверка базы знаний замечает, если сгенерированные файлы устарели.

#### Почему 269 ручных и 260 сгенерированных

**Ручные** правила (PRF … GOL) — настоящие знания эксперта, каждое придумано и обосновано отдельно. **Сгенерированные** — это знание, разложенное по табличкам: в таблице чипсетов по сути одно правило «плата не потянет процессор мощнее своего предела», повторённое для каждого из 27 чипсетов. Для машины вывода это полноценные отдельные правила, каждое со своим кодом, объяснением и записью в трассе.

## 2.3 Факты и рабочая память

### Факт

Факт — одно утверждение о текущей ситуации. У него есть:
- **путь**: что это (`req.ram_min_gb`);
- **значение**: `32`;
- **уверенность**: насколько система в этом уверена, `0.8`;
- **источник**: откуда взялся (ответ клиента, каталог, правило `REQ-024`, вычисление).

### Пространства имён фактов

| Путь начинается с | Что это | Откуда берётся |
|---|---|---|
| `user.*` | Ответы клиента: бюджет, разрешение, задачи | Визард |
| `profile.*` | Выводы о клиенте: веса сценариев, главный сценарий | Правила PRF |
| `req.*` | Требования к деталям: мин. VRAM, класс GPU, нужна ли дискретная видеокарта | Правила REQ |
| `budget.*` | Доли бюджета по категориям | Правила BUD |
| `cand.*` | Товар, который проверяется прямо сейчас | Конфигуратор, этап фильтрации |
| `build.<категория>.*` | Деталь в собираемой сборке (`build.gpu.length_mm`) | Конфигуратор, этап поиска |
| `perf.*` | Прогноз производительности | Модель производительности |

Кроме деталей, в сборке есть итоговые факты: `build.total.price_rub` (цена), `build.total.power_w` (оценка потребления: TDP процессора + TBP видеокарты + 75 Вт на прочее) и отметки `build.<категория>.owned` («деталь уже есть у клиента»).

### Словарь фактов

Какие факты вообще бывают, записано в **словаре фактов**: путь, тип (число, да/нет, строка, список), допустимые значения и кто его устанавливает (клиент, правило, каталог). По словарю проверка базы знаний ловит опечатки: правило с условием `user.resolutoin = 1440p` или `user.color = фиолетовый` не пройдёт проверку.

### Как ответы становятся фактами

Вопросы визарда описаны в **анкете** (файл с вопросами, вариантами ответов и тем, в какой факт записать ответ):

| Вид вопроса | Пример | Что записывается |
|---|---|---|
| Задачи | Основная — игры, иногда — монтаж | `user.weight.<задача>` для **всех** восьми задач: основная 1.0, дополнительные 0.3, остальные 0 |
| Число | бюджет | `user.budget = 170000` |
| Выбор | цвет корпуса; монитор | `user.color = white`; вариант «не важно» факта не даёт. Вариант может записать сразу несколько фактов: «2K, 144–180 Гц» → `user.resolution = 1440p`, `user.refresh_hz = 144` |
| Несколько вариантов | игры | `user.games = [baldurs_gate_3, cyberpunk_2077]` |
| Да / нет | «Нужна подсветка?» | «да» / «нет» — уверенность 1.0, «скорее да» / «скорее нет» — 0.6, «не знаю» — факт не записывается |

Веса записываются для всех задач, даже неотмеченных, чтобы правила могли сравнивать их между собой («игры важнее всего остального»).

**Почему 1.0 и 0.3.** Пороги в правилах делятся на два вида:
- **≥ 0.4** срабатывает только от основной задачи: главный сценарий и жёсткие требования вроде «для монтажа нужно 32 ГБ»;
- **≤ 0.3** срабатывает и от дополнительной: вторичный сценарий, класс игровой нагрузки, требования стриминга.

Поэтому «иногда монтирую» добавит монтаж в оценку сборки и в советы, но не потребует 32 ГБ, как для профессионального монтажа. Оба числа записаны в анкете: их можно поменять без программиста, но тогда нужно проверить пороги правил.

Раньше задачи задавались восемью ползунками 0–100%. От них отказались: ползунок на 30% и на 100% при одном и том же намерении «только игры» давал разные сборки, а при равных ползунках главной становилась задача, стоящая первой в списке.

### Рабочая память

Рабочая память — «блокнот» одной консультации. В начале в нём только ответы клиента. По мере работы правил туда дописываются выведенные факты. Каждый клиент начинает с чистого блокнота, консультации друг на друга не влияют.

### Как знания связаны между собой

```
  Фреймы  ──задают──►  какие пути фактов существуют и какого они типа
     │                          ▲
     │ экземпляры               │ проверяются при публикации правил
     ▼                          │
  Каталог ──даёт факты──►  build.* / cand.*
                                │
  Ответы  ──дают факты──►  user.*
                                │
  Правила ──читают факты, пишут новые──►  profile.* / req.* / budget.*
```

Правило не может сослаться на несуществующую характеристику. Если инженер знаний напишет `build.gpu.lenght_mm` (с опечаткой), проверка при публикации ответит: «слот `lenght_mm` не существует во фрейме „Видеокарта“». Это защищает от тихих ошибок, когда правило просто никогда не срабатывает.
