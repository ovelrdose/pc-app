# ADR 0004. Наполнение базы знаний: словарь фактов, анкета, соглашения по CF, файлы до этапа 6

- Статус: принято
- Дата: 2026-10-29
- Затрагивает: `docs/architecture.md` §5.2, §6, §7.2, §14; `knowledge/`; код
  `backend/app/expert/{vocabulary,questionnaire,tables,generation,validation,knowledge,consultation,golden}`

## Контекст

Этап 4 наполняет базу знаний (≥ 500 правил) и вводит статические проверки. Архитектура
описывала пространства имён фактов (§5.2) и проверку «путь существует во фреймах» (§6.2), но не
задавала, где перечислены пути `user.*`, `profile.*`, `req.*`, `budget.*`, и как ответы визарда
становятся фактами. При наполнении также выяснилось, как конфликт значений (ADR 0002) влияет на
требования.

## Решения

1. **Словарь фактов в коде** (`expert/vocabulary.py`) — фрейм «Профиль клиента»: путь, тип,
   допустимые значения и роль (вход / вывод правил / каталог / вычисление). Пути `cand.*` и
   `build.<категория>.*` выводятся из фреймов комплектующих. Новый путь — правка кода, как и
   новый слот фрейма (вики §3.6).

2. **Анкета** (`knowledge/questionnaire.yaml`) — данные: шаги, вопросы, варианты и факт для
   каждого ответа. Веса задач записываются для всех восьми сценариев (неотмеченные = 0), чтобы
   правила могли сравнивать веса. «Да/нет» — CF 1.0, «скорее» — 0.6, «не знаю» — факта нет.

3. **Генератор: состав семейств.** GEN-SKT — 3 правила на сокет (чипсет своей платформы, тип
   памяти, баллы за перспективность); GEN-CHP — предел TDP процессора для всех чипсетов (замена
   классу VRM платы), предупреждение о разгоне для чипсетов без разгона, баллы за PCIe 5.0;
   GEN-FF — плата ↔ корпус, БП ↔ отсек, размер корпуса, компактность; GEN-GAME — 3 пресета на
   игру, подцели `fps_at_least` и `vram_enough` (встроенные предикаты модели производительности,
   этап 5); GEN-APP — 2 уровня на программу, подцель `bench_at_least`. Итого 260 правил.

4. **Соглашение по CF требований.** При конфликте значений побеждает больший CF, а CF затухает по
   цепочке правил (0.85 × 0.85 = 0.72). Поэтому базовые требования («игры → 16 ГБ») получают
   CF ≈ 0.6 (обязательные, но проигрывают конкретным), а желательные — CF < 0.5 / итог < 0.5.

5. **Валидатор** (`expert/validation`, `scripts/validate_kb.py`) реализует §6.2: уникальность,
   компиляция, пути и типы по словарю, вывод только в выводимые факты, неизвестные предикаты
   целей, циклы (пометки «разрешённый цикл» нет — любой цикл ошибка), противоречия, недостижимые
   посылки; предупреждения — избыточность, неиспользуемые выводы, правила filter/compat/score без
   «предмета в руках». Отдельно проверяется актуальность сгенерированных файлов.

6. **Golden cases** (`knowledge/golden/*.yaml`, `expert/golden.py`): ответы визарда и ожидания
   (выполнимость, минимальный бюджет, факты, сработавшие правила, отсеянные товары, свойства
   каждого варианта, замечания и баллы). Ожидания по FPS и целям — этап 5.

7. **Score-правила в поиске.** Баллы score-правил начисляются частичной сборке, как только в ней
   есть все упомянутые детали (как forward checking для compat). Без этого штрафы за дисбаланс
   учитывались только на готовых сборках, и луч отбрасывал сбалансированные варианты (уточняет
   ADR 0003).

8. **Хранение правил и снимков в БД переносится на этап 6.** На этапе 4 источник истины — файлы
   `knowledge/`, снимок (`KnowledgeSnapshot`) собирается из них. Таблицы `rules`,
   `rule_revisions`, `kb_snapshots`, `reference_*` и публикация появятся, когда их начнёт
   использовать API (этап 6) и админка (этап 9). Seed на этапе 4 сверяет статусы каталога со
   справочниками (`needs_kb`).

## Последствия

- 529 правил (269 ручных, 260 сгенерированных), валидатор без ошибок и предупреждений,
  16 golden cases.
- Опечатки в путях и типах ловятся до запуска, а не тихим «правило не сработало».
- Сквозные прогоны на реальном каталоге нашли и исправили четыре ошибки знаний (требования
  киберспорта к видеокарте, 64 ГБ для «высокого» бюджета, затухание CF у 32 ГБ, обязательность
  32 ГБ для вторичного монтажа) и одну ошибку поиска (п. 7).
