# ADR 0005. Модель производительности, факты perf.*, обратный вывод и объяснения

- Статус: принято
- Дата: 2026-10-29
- Затрагивает: `docs/architecture.md` §5.6, §7.3, §7.7, §8; `knowledge/tables/applications.yaml`;
  правила BAL; код `backend/app/expert/{performance,inference/backward,hypotheses,explanation}`

## Контекст

Этап 5: модель FPS и бенчмарков, гипотезы, «почему не», невыполнимые требования. Формулы §8
заданы, но не определены числа поправок, роль трассировки, встроенная графика, нормировка
полезности и то, как правила баланса узнают прогноз. При внедрении модели выяснилось, что
BAL-правила этапа 4, сравнивавшие индексы CPU и GPU напрямую, дают ложные предупреждения:
для сборки с RX 9070 XT и i5-14400F правило писало «процессор сдерживает видеокарту», а прогноз
в Cyberpunk 2077 1440p показывает упор в видеокарту (соотношение 1,09).

## Решения

1. **Модель FPS** (`expert/performance`): формулы §8. Поправка на ОЗУ: 8 ГБ — 0,88, 16 — 0,98,
   32 — 1,01, 64+ — 1,02; одна планка −0,05; DDR5 от 6000 +0,02; DDR4 медленнее 3200 −0,02;
   итог в [0,85; 1,05]. Трассировка: индекс `perf_rt` и множитель 0,6 к базовому FPS; игры с
   `rt_required` всегда считаются с RT. Встроенная графика — индекс 12, 2 ГБ памяти.

2. **Программы**: в справочник добавлены `task`, `ref_minutes` (время на эталонной системе) и
   `min_index` уровней. Индекс нагрузки: `cpu_single` → `perf_single`, `cpu_multi` → `perf_multi`,
   `gpu` → `perf_raster`, `mixed` → среднее многоядерного и GPU. Время = эталон × 100 / индекс.
   Бенчмарки: значение из карточки или оценка по индексу (Cinebench 2024 112/945,
   Time Spy 10 500, Steel Nomad 2 600 у эталона), с пометкой «оценка».

3. **Полезность по FPS** (`FpsPerformanceModel`) заменяет временную модель на индексах (ADR 0003)
   в консультации: игровые сценарии — средний FPS в играх клиента (или типовом наборе) на его
   разрешении относительно эталонной сборки = 100, FPS выше частоты монитора × 1,25 пользы не
   добавляет; эталон считается с той же поправкой на RT. Неигровые сценарии — по индексам.
   Модель на индексах остаётся для подбора без анкеты (тесты конфигуратора).

4. **Факты `perf.*`** для правил: `perf.fps_avg`, `perf.bottleneck_ratio`, `perf.gpu_utilization`,
   `perf.limited_by` — по играм главного игрового сценария клиента. Правило, читающее `perf.*`,
   считается зависящим от процессора и видеокарты (триггер для поиска). BAL-правила баланса
   переписаны на эти факты (коды сохранены). Коридор «сбалансировано» для игр — 0,85–2,0:
   умеренный упор в видеокарту в AAA-играх нормален.

5. **Обратный вывод** (`inference/backward.py`): поиск в глубину по goal-правилам с
   унификацией аргументов головы, дерево с узлами `proved/failed/unknown`. Переменная `$x`
   берётся из ответа клиента на вопрос, затем из факта (`ASKABLE`: `resolution` →
   `user.resolution`, `target_fps` → новый входной факт `user.target_fps`), иначе узел
   «неизвестно» и вопрос клиенту. Отсутствующий факт сборки — «опровергнуто» («в сборке этого
   нет»), отсутствующий факт клиента — «неизвестно». Встроенные предикаты `fps_at_least`,
   `vram_enough`, `bench_at_least` вычисляет модель. Защита: глубина 8, цикл целей — «опровергнуто».

6. **«Почему не»** реализовано прямой проверкой, а не доказательством цели
   `compatible(build + X)` (§5.6): вердикты «не найден / уже в сборке / категория не нужна /
   уже есть у клиента / недоступен / отсеян правилом / несовместим (все нарушенные правила) /
   не влезает в бюджет / хуже (Δ полезности и Δ FPS) / не хуже (можно подставить)». Прямая
   проверка даёт то же объяснение (нарушенные compat-правила) проще и быстрее.

7. **Невыполнимые требования** (§7.7) реализованы перебором, а не целью `satisfiable(req)`:
   (а) мешающие требования — обязательные `req.*`, которые читают фильтры, снимаются по одному и
   пересчитывается цена самой дешёвой совместимой сборки; (б) ослабления ответов — разрешение и
   частота на ступень ниже, SSD меньше, «любой» цвет/размер/бренд, без стекла/RGB/Wi-Fi/HDD;
   (в) лучшая сборка в бюджете без обязательных требований и список нарушенных фильтров.
   Разбор занимает 2–3 с и вызывается по запросу, а не при каждом подборе.

## Последствия

- Golden cases проверяют FPS, время в программах, гипотезы (в том числе GOL, GEN-GAME, GEN-APP),
  «почему не» и разбор невыполнимых запросов.
- Прогноз и баланс согласованы: правило баланса и карточка сборки опираются на одни и те же
  цифры.
- Числа игр и программ — оценки по открытым обзорам; их уточнение — правка справочников без кода.
