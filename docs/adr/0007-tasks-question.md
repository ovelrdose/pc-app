# ADR 0007. Задачи в визарде: основная и дополнительные вместо слайдеров весов

- Статус: принято
- Дата: 2026-10-30
- Затрагивает: `docs/architecture.md` §5.2, §5.4, §11; `knowledge/questionnaire.yaml`; код
  `backend/app/expert/questionnaire.py`, `frontend/src/features/wizard`

## Контекст

Первый шаг визарда спрашивал задачи восемью слайдерами 0–100%. Каждый слайдер записывался как
абсолютный вес (30% → `user.weight.<задача>` = 0.3). Оценка сборки нормирует веса, то есть
учитывает соотношение. Правила же сравнивают веса с абсолютными порогами: 0.1 (задача
учитывается), 0.25–0.3 (вторичный сценарий, игровой класс), 0.4 (главный сценарий), 0.5
(жёсткие требования). Проверка на ядре показала три проблемы.

1. **Одно намерение — разные сборки.** «Только игры» со слайдером на 100% включает требование
   к видеокарте, а на 30% не включает. Бюджет 100 000 ₽, отказ против RTX 3050.
2. **Ничья выбирает первый вариант.** Игры, офис и программирование по 100% делают главным
   сценарием офис: он первый в списке.
3. **Подсказка в интерфейсе неверна.** «Важно соотношение» верно для оценки, но не для правил.

Пользователю непонятно, тянуть ли каждый слайдер и что значит «40%».

## Решение

1. **Новый вид вопроса `tasks`.** Вопрос состоит из двух частей: основная задача (ровно одна,
   обязательна) и дополнительные (сколько угодно, можно пропустить). Ответ хранится как
   `{"main": "aaa_gaming", "extra": ["video_editing"]}`. Ответ переводится в те же факты, что
   раньше:
   - `user.weight.<основная>` = `main_weight` (1.0);
   - `user.weight.<дополнительная>` = `extra_weight` (0.3);
   - остальные задачи = 0.

   Оба веса заданы в анкете и относятся к знаниям, а не к коду. Если основная задача попала и в
   дополнительные, побеждает основная.
2. **Смысл порогов правил:**
   - ≥ 0.4 — «только основная задача» (главный сценарий, жёсткие требования);
   - ≤ 0.3 — «основная или дополнительная» (вторичный сценарий, игровой класс, стриминг).

   Вес 0.3 выбран так, чтобы прежний сквозной пример «игры 70%, монтаж 30%» переводился без
   изменения результата.
3. **Главный сценарий всегда единственный.** Ничьих больше нет.
4. **Правило PRF-029** «Игры и творческие задачи одновременно» требовало вес ≥ 0.5 у обеих
   групп. При одной основной задаче такое невозможно. Новое условие: творческая задача основная
   (≥ 0.5), игры дополнительные (≥ 0.3). Код правила сохранён, смысл («нужен запас по памяти и
   ядрам») не изменился.
5. **Слайдеры убраны** из анкеты и интерфейса. Тип `weights` остаётся в ядре только для чтения
   ранее опубликованных снимков БЗ: сохранённые сборки пересчитываются по своему снимку и
   должны открываться. В новой анкете проверка БЗ считает его ошибкой.
6. **Совет про объём SSD** (BAL-031) срабатывает и для дополнительной задачи «современные игры»:
   порог снижен с 0.5 до 0.3. Требование 1 ТБ (REQ-033) по-прежнему идёт только от основной
   задачи. Эталонный кейс G-021.
7. **«Изменить ответы»** для консультаций со старыми ответами: у вопроса новый id `tasks`,
   поэтому старый ответ `purposes` не подставляется. Задачу нужно выбрать заново, остальные
   ответы сохраняются.

## Последствия

- Одинаковое намерение всегда даёт одинаковые факты. Пользователь отвечает на два понятных
  вопроса вместо настройки восьми слайдеров.
- Тонкая настройка («игры 60%, стриминг 50%») больше невозможна. Для покупателя это не
  потеря: такие различия не меняли сборку предсказуемо.
- Эталонные кейсы переведены на новый формат. G-001 потерял ответ «стриминг 20%»: раньше он был
  ниже всех порогов и ни на что не влиял. Новые кейсы:
  - G-019 — игры и иногда стриминг (вывод «многозадачность», 32 ГБ ОЗУ);
  - G-020 — монтаж и иногда игры (PRF-029).
