# ADR 0006. API клиента: БЗ в БД, контекст сборки, владелец — на этапе 8

- Статус: принято
- Дата: 2026-10-29
- Затрагивает: `docs/architecture.md` §4.2, §6.1, §9, §10; код `backend/app/{models,repositories,services,api}`

## Контекст

Этап 6 — первое API, которое использует опубликованную базу знаний. До сих пор (ADR 0004)
источником знаний были файлы `knowledge/`. Нужно решить, как знания попадают в БД, как сохранять
сборки так, чтобы по ним можно было объяснять, проверять гипотезы и править, и что делать с
проверкой «владелец сборки» до появления аккаунтов (этап 8).

## Решения

1. **Таблицы БЗ.** `rules` (рабочая копия, `body` — правило целиком в JSON), `rule_revisions`
   (история), `reference_tables` (одна таблица: имя → JSON; справочники `sockets`, `chipsets`,
   `form_factors`, `games`, `applications` и анкета `questionnaire`) вместо трёх таблиц
   `reference_games/apps/tables` из §9 — структура справочников и так задаётся схемами Pydantic,
   а одна таблица проще для импорта, экспорта и снимков. `kb_snapshots` хранит правила,
   справочники и анкету снимка.

2. **Импорт и публикация.** Seed импортирует `knowledge/` в рабочую копию (новые правила —
   ревизия 1, изменённые — новая ревизия и запись истории, отсутствующие в файлах не трогаются;
   дополнение 2026-10-30: правила из реестра `rules/retired.yaml` выключаются, см. §6.1) и
   публикует снимок: компиляция, статические проверки, golden cases (в seed — по умолчанию,
   `--skip-golden` для быстрого прогона). Снимок с тем же содержимым (SHA-256) повторно не
   создаётся. При публикации пересчитываются статусы каталога по справочникам снимка (§17).

3. **Кэш снимков** в памяти процесса: скомпилированные снимки БЗ по id (до 4 последних) и каталог
   по `catalog_revision` с соответствием артикул ↔ id строки.

4. **Сборка хранит**: детали с ценой на момент расчёта, полезность, прогноз (JSON карточки),
   трассу консультации, замечания и баллы, ограничения поиска (имеющиеся, зафиксированные,
   исключённые детали, переопределённые доли) и снимок БЗ. Профиль клиента не хранится целиком:
   для объяснений, «почему не», гипотез и правок он заново выводится из ответов на **том же**
   снимке (ядро детерминировано), а план и фильтрация пересчитываются на текущем каталоге.

5. **Варианты** сохраняются по строке на вариант, даже если два варианта совпали; клиент
   объединяет одинаковые составы сам (§7.4).

6. **Альтернативы** (`/builds/{id}/alternatives`) — все совместимые замены категории, включая
   выходящие за бюджет (с вердиктом `over_budget`): сначала укладывающиеся в бюджет, по убыванию
   прироста полезности.

7. **Владелец** — этап 8. Колонки `consultations.user_id` и `guest_session_id` уже есть (без
   внешних ключей: таблиц пользователей и сессий ещё нет). До этапа 8 эндпоинты консультаций и
   сборок открыты; `GET /me/builds` появится вместе с аккаунтами.

8. **Транзакция на запрос**: сессия фиксируется после успешного обработчика и откатывается при
   исключении.

9. **PDF** — WeasyPrint по HTML-шаблону Jinja2 (`app/templates/build.html`), шрифт DejaVu Sans
   (кириллица). Системные Pango и HarfBuzz на машине разработки уже установлены.

10. **Имеющиеся детали в консультации** (дополнено на этапе 7): `ConsultationOut.owned` — детали,
    которые уже есть у клиента (id, категория, название, цена в каталоге). Нужны клиенту, чтобы
    «Изменить ответы» и «Подобрать с этим» не теряли их: в сборках имеющаяся деталь видна, но в
    невыполнимой консультации сборок нет.

## Последствия

- Сквозной сценарий клиента проверяется интеграционными тестами через HTTP на `pcapp_test`.
- Изменение правил после публикации не меняет старые сборки: они объясняются на своём снимке.
- Изменение цен меняет только новые сборки: в старых цена зафиксирована.
